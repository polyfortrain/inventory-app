# テスト仕様書

> Issue #18「テスト仕様書を作成する」の成果物。**この文書はテストの設計であり、テスト実施・合格を意味しない。**

## 1. 目的と対象範囲

在庫管理Webアプリケーションが、要件定義書の **FR-01〜FR-06** を満たすことを確認する。ブラウザ操作による機能テストを中心に、正常系・異常系・境界値・保存結果を検証する。

- **対象：** 在庫一覧、登録、更新、削除、入力チェック、データ保存。
- **対象外：** ログイン、検索、入出庫履歴、インターネット公開、性能負荷テストなど。
- **テスト水準：** 実装後の画面操作による結合〜システムテストを想定。Java単体テストの仕様ではない。
- **テスト実施状態：** すべて未実施。実装後に別途実施・記録する。

**参照資料：** [要求・要件定義](../requirements/requirements-definition.md) ／ [ユースケース仕様書](../requirements/use-cases.md) ／ [画面仕様書](../external-design/screen-design.md) ／ [テーブル定義書](../internal-design/table-definitions.md) ／ [シーケンス図](../internal-design/sequence-design.md)

## 3. テストの進め方・共通データ

**準備データ**（実際の在庫IDは自動採番なので固定しない）：

| セット | 内容 |
|---|---|
| `D0` | 在庫レコードが0件 |
| `D1` | 2件登録：在庫A「ねじ」数量12、在庫B「ナット」数量5 |

テストケースは原則として**互いに独立**して実施し、指定されたD0またはD1へ初期化してから開始する。実際のIDは実行時に控える。必要があれば実施前後に一覧とテストDBの内容を比較する。

**1件のテストケースの実施手順：** (1) 初期データを用意 → (2) 表の「操作・入力」を実行 → (3)「期待結果」と実際の結果を比較 → (4) [テスト実施記録](test-execution-log.md)または付属Excelに結果・証跡を記録。

- **必須ケース：** 合格条件の対象。
- **任意ケース：** 品質向上用の追加検証。実施前に手順・期待結果をレビューで確定する。
- **在庫名の長さ：** 「あ」を100回／101回繰り返した文字列を使用する（1文字と100文字の境界）。
- **存在しないID：** 現在のテストDBに存在しない番号を確認して使用し、実装後に直接リクエスト等の方法を確定する。
- **画面ID：** SCR-01=在庫一覧、SCR-02=在庫登録、SCR-03=在庫更新、DLG-01=削除確認。

## 4. テストケース

各行の「前提」は上記D0/D1を指す。**登録・更新・削除が失敗するケースでは、対象データだけでなく他のデータも変更されない**ことを確認する。

**記入・判定の例（TC-015）：** (1) テストDBをD0にする → (2) 登録画面で在庫名「上限外」・数量「1000000」を入力する → (3) 登録を押す → (4) エラー表示・DB未登録を確認する → (5) 一致すればOK、違えばNGとして証跡と不具合Issueを記録する。

## 5. テスト結果の判定・不具合管理

| 状態 | 判定方法 |
|---|---|
| 未実施 | まだテストしていない |
| OK | 実際の結果が期待結果と一致する |
| NG | 期待結果と異なる／データが意図せず変更された |
| 保留 | 環境・未実装・不具合等により実施できない |
| 対象外 | 実施不要とレビューで判断し、理由を記録した |

NG時は**テストID、実行手順、期待結果、実際の結果、証跡、再現条件、GitHub Issue番号**を残す。修正後は同じテストを再実施して再判定する。

**完了の目安（今回の計画案）：** 必須37件がすべて実施されOKであること。NG・保留が残る場合はIssueを起票し、対応方針を明確にすること。任意3件は別途採否を決める。
